# V26.3.9 — CANONICAL COMMIT / HYDRATION / INDEX REBUILD

## Root-cause fix
V26.3.8 committed `chat["conversation_record"]` by replacing the persisted canonical snapshot. If a Streamlit rerun exposed only the current RequestRecord, that narrower record could overwrite the previously persisted historical Message/Request/Round collections. The audit then correctly read the canonical object—but the canonical object had already been narrowed—producing `UNIQUE_REQUEST_IDS = 1`.

## V26.3.9 changes
- Canonical commit is now append-only by immutable Message/Request/Round identity.
- A narrower current rerun can never erase an older committed Request, Message, or Round.
- Canonical commit rebinds the live chat object to the complete merged canonical record.
- Hydration rebuilds runtime indexes from the complete canonical record.
- Runtime indexes are non-authoritative derived indexes; they never become a second source of truth.
- Provider/result lifecycle mutations are committed back into the same canonical RequestRecord before orchestrator return.
- Authoritative historical audit remains canonical-record-only and has no current-request fallback.
- Existing V26 persistence namespace is retained only as a compatibility mirror populated from the merged canonical record.
- No Provider Core, Free Cascade, Secrets, or Model Lists changes.
- No existing files were removed.

## Required runtime proof
For two independent messages in one Conversation, Application-Owned Runtime State must show:
- HISTORICAL_MESSAGE_COUNT = 2
- HISTORICAL_REQUEST_COUNT = 2
- HISTORICAL_ROUND_COUNT = 2
- distinct MESSAGE_ID_1 / MESSAGE_ID_2
- distinct REQUEST_ID_1 / REQUEST_ID_2
- distinct ROUND_ID_1 / ROUND_ID_2
- correct Message→Request and Request→Round mappings
- PREVIOUS_REQUEST_REEXECUTED = NO
- TWO_MESSAGE_ISOLATION = PASS
- HISTORICAL_SOURCE = V26_3_CONVERSATION_PERSISTENCE / canonical ConversationRecord
- AUTHORITATIVE_SOURCE = APPLICATION_OWNED_RUNTIME_STATE

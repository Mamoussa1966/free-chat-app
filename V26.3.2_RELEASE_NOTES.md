# V26.3.2 — CANONICAL CONVERSATION PERSISTENCE / HISTORICAL IDENTITY GATE

## Root-cause correction
V26.3.1 could still expose the historical ledger through a session-state path while the authoritative audit observed only the current/narrowed runtime view during rerun/hydration.

V26.3.2 makes the application-owned `v26_3_conversation_persistence` embedded in the canonical Conversation object the sole historical identity source for the authoritative gate.

## Required chain
- Conversation → MessageRecord #1 → Request #1 → Round #1
- Conversation → MessageRecord #2 → Request #2 → Round #1

## Persistence contract
- Message identity is allocated once before provider execution.
- Message→Request is persisted before provider execution.
- Round→Message→Request is persisted at round start and completion.
- Records are append-only by stable identity; conflicting bindings are retained as `identity_conflict` and never silently overwritten.
- Streamlit `session_state` is a compatibility mirror only; it cannot narrow or replace canonical conversation history.
- Hydration is additive and identity-preserving.

## Authoritative Audit contract
The audit reads only `chat["v26_3_conversation_persistence"][conversation_id]`.
It must expose:
- MESSAGE_ID_1 / MESSAGE_ID_2
- REQUEST_ID_1 / REQUEST_ID_2
- ROUND_ID_1 / ROUND_ID_2
- Message→Request mapping
- Round→Message mapping
- historical request count and IDs
- PREVIOUS_REQUEST_REEXECUTED
- TWO_MESSAGE_ISOLATION

If canonical history is incomplete, the gate returns `NOT_PROVEN` rather than falling back to a current-only ledger.

## Scope guard
No provider selection, Free Cascade policy, credentials, model lists, Transactional Bridge implementation, or HOTFIX131 prose-isolation logic is changed by this hotfix.
